# Authorised hosting installation and verification

This package is for the existing voxelveda.com mail relay, not a new provider or website. It includes locked production PDF-parser dependencies and the exact tested receiver source. `SOURCE_COMMIT` identifies the packaged workflow checkout; verify the supplied ZIP checksum. Inclusion in a successful application release does not prove installation here.

1. In the existing secure hosting/WordPress administrator session, identify the plugin, must-use plugin or code snippet currently registering `voxel-veda/v1/mail-relay` and `/mail-relay/health`. Inspect active SMTP/mail plugins and `pre_wp_mail`/PHPMailer hooks. Back up the current receiver and relevant configuration outside the public web root. Record a rollback procedure. Do not replace unrelated plugins or update WordPress as part of this repair.
2. Retain the existing `info@voxelveda.com` sender, provider and secret. This receiver reads `VOXEL_VEDA_MAIL_RELAY_TOKEN` from the host's secure configuration. Reuse the existing shared secret securely; never place it in source, a URL, support report or chat. If the current receiver stores that secret differently, map it through the existing protected hosting configuration before activation. Do not rotate it blindly or change Railway's value.
3. Install `voxel-veda-pdf-relay.zip` through the authorised plugin upload/hosting workflow. Remove the old receiver's ownership of these exact routes before enabling this one. Keep the backup available. Do not run two route owners or allow a bypassing API mail adapter to claim native MIME support. The prepared receiver fails closed if final recipient/body/attachment integrity cannot be observed.
4. Using a secure local client with the existing token supplied as a header, test GET `https://voxelveda.com/wp-json/voxel-veda/v1/mail-relay/health`. Unauthenticated requests should remain JSON 401. A successful authorised response must be JSON with `ok:true`, `weekly_html_contract_version:1`, `weekly_html_content_preserved:true`, and `weekly_recipient_privacy_enforced:true`. PDF documents additionally require the version-3 attachment/parser capability flags. If a mail hook prevents those capabilities, inspect its actual transport implementation; do not disable security/provider hooks blindly.
5. Confirm the currently configured Railway relay URL securely. Preserve this existing provider and pretty REST endpoint. Public probes on 28 October showed the pretty WPVibe health path answered JSON while root `?rest_route=` paths returned homepage HTML. Authenticated application health still reported a non-JSON response. Inspect the exact configured request and host/origin logs, including redirects/cache/security routing. A public 401 or one working path does not prove the authenticated application path. No broad firewall exception is justified by this evidence.
6. Report only non-secret evidence: plugin/source commit, backup identifier, active route owner, health status/capability booleans, relevant error code and UTC time. This allows the application operator to recheck its own authenticated health before any send. Never include credentials, cookies, sensitive reports or a raw configuration dump.
7. After health succeeds, coordinate one synthetic controlled report to the session's authorised test inbox. Do not use employee reports for testing or trigger historical backfill. Check one To, no CC/BCC, complete matching HTML and plain text, zero attachments for the HTML-only test, actual provider result/message ID and received body on phone/desktop. Other document tests must decode and parse genuine PDF attachments with `.pdf` names. Provider acceptance is not inbox receipt.

If activation/health fails, restore the previous receiver/configuration from the protected backup without deleting acceptance/idempotency history, rotating keys or resending uncertain attempts. Retain request locks and prior receipts. The prepared plugin's option keys suppress duplicate request IDs; do not clear them as routine cleanup.

No purchase, provider switch, DNS change, historical attendance correction or designated employee address change is part of this hosting procedure. The eligible employee must save a genuine designated timesheet address through the authorised profile workflow; it must not be inferred from a login or test inbox.
