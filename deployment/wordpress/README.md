The production relay receiver is outside this repository and was not accessible during this repair. This plugin is a concrete receiver repair, pending installation and recipient verification; its inclusion does not imply the live WordPress relay was changed.

Install dependencies with `composer install --no-dev --classmap-authoritative`, then install the plugin directory in the existing authorised WordPress hosting. Configure `VOXEL_VEDA_MAIL_RELAY_TOKEN` in the WordPress secret configuration using the existing Railway relay token; do not copy tokens into source control. Retain the existing company mail provider and verified `info@voxelveda.com` sender. The plugin supports the production `/wp-json/voxel-veda/v1/mail-relay` and matching `/mail-relay/health` routes; disable or replace the old receiver that owns those routes before activation, then verify the health response using the existing token. Railway's existing relay URL remains unchanged. The alternate `/mail` route is optional and requires an explicitly reviewed configuration change; the app does not select it automatically. No DNS, plan or provider change is needed for this HTTPS transport.

The receiver parses each PDF with Smalot PdfParser, requires a page, checks the length/hash, and uses PHPMailer `addStringAttachment(bytes, originalPdfFilename, 'base64', 'application/pdf', 'attachment')`. It does not create attachment temporary files. This removes the common receiver-side `wp_tempnam()` filename leak by making the MIME filename explicit. That mechanism must be confirmed against the inaccessible live receiver or a received MIME message before claiming it was the historical production cause.

Stable request IDs suppress repeated sends after provider acceptance and uncertain outcomes require review. A false result or exception after the attempted `wp_mail` call retains `REVIEW_REQUIRED`; it does not delete the request lock or automatically resend. `wp_mail` success means provider acceptance only. The successful response binds each parsed attachment to its exact filename, MIME type, bytes, hash and page count; the application checks those fields again. Do not mark recipient receipt or opening verified from this response. Verify a controlled authorised inbox's decoded MIME and opened attachment after installation.

The health contract deliberately returns `pdf_bytes_validated: false` when the parser is absent and disables PDF filename capability when a `pre_wp_mail` filter can bypass native PHPMailer MIME construction. Such a provider adapter requires an explicitly reviewed attachment implementation; do not silently disable its filter or switch providers. After every native document attempt, the receiver confirms the observed PHPMailer attachment bytes, filenames, MIME type and disposition again. Missing hooks or altered parts require review despite a successful `wp_mail` result. The application refuses PDF email before sending to an incompatible relay. Normal invitation/password-reset mail remains available. Failed PDF deliveries remain in the application's durable queue for explicit retry after receiver repair. Plugin provider-acceptance entries must be retained for at least as long as the application retry history; do not delete them as routine cleanup.

Weekly timesheets also support an explicit **HTML-only** format, independent of the attachment contract and PDF parser. New HTML requests include `weekly_html_contract_version: 1` and a `delivery_policy` with `format: "HTML"`, `layoutVersion: "weekly-html-v1"` and `contentHash`. The content hash is SHA-256 of UTF-8 JSON with ordered keys `subject`, `html`, `text`, `layoutVersion`, unescaped Unicode/slashes/line terminators. The application freezes these complete alternatives against the employee/week/version source snapshot. The receiver requires both alternatives, no attachments, exactly one designated To and no CC/BCC. It validates the hash before attempting mail and checks the actual final PHPMailer subject, HTML, plain text, recipients and zero attachments before and after the transaction. A logo is a remote image with useful text/alt content, never an added image attachment.

HTML health capability is `weekly_html_contract_version: 1`, `weekly_html_content_preserved: true`, plus `weekly_recipient_privacy_enforced: true`. None requires `pdf_bytes_validated` or the attachment contract. A successful HTML result binds `request_id`, `layout_version`, `weekly_html_sha256`, `designated_recipient` and `attachments: []`. Any actual MIME `message_id` is separate from the request ID and does not verify receipt. Active API hooks that bypass native body/envelope construction cannot advertise this capability without a reviewed provider implementation. A broken/non-JSON relay response is still a transport blocker; optional PDF removal does not establish a healthy receiver.

Accepted receipts now bind the full original message fingerprint. A repeated accepted key returns its receipt only for matching content/recipients; a changed report or designated address needs an authorised new revision, never a rewrite. Pending/uncertain outcomes stay held for review. Existing accepted PDF receipts, PDF-only document validation and attachment-free account messages remain compatible.
