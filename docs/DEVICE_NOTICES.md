# Mobile entry and device notices

Ordinary users receive a 96-hour session from full sign-in. Short access credentials renew through the existing MySQL session record. The original deadline never moves. Existing sessions keep their original expiry. Admin and other privileged sessions remain capped at two hours, with the existing step-up verification on sensitive operations. Railway's production service listed no `JWT_EXPIRES_IN`, `PRIVILEGED_SESSION_EXPIRES_IN` or cookie-expiry override during review. `JWT_EXPIRES_IN` cannot override the new ordinary limit.

An installation can opt into public releases on sign-in, in Settings or in its profile. Its random installation credential is separate from the authenticated cookie. An explicitly enrolled personal installation can additionally receive generic AI Team alerts. The account must be an active allowlisted admin or super admin, with push enabled in AI Team preferences. A release opt-in survives logout. Keeping generic team alerts after manual logout requires its own explicit choice. Account switch, unlink, revoked session and account access changes stop the applicable bindings. Reopening private activity always passes through page authentication and the permitted-owner feed API.

## Provider setup

1. Apply the normal reviewed additive migrations. Set `DEVICE_PUSH_WORKER_ENABLED=true` only after configuring at least one provider below. Delivery rows are unique per installation and release or activity. Explicit throttling is retried with backoff. Requests with uncertain provider outcome are held as uncertain, so an accepted-but-unconfirmed request cannot be blindly repeated. Provider acceptance and actual displayed delivery are distinct.
2. Web Push uses `DEVICE_PUSH_VAPID_PUBLIC_KEY` and `DEVICE_PUSH_VAPID_PRIVATE_KEY`. Generate one persistent VAPID key pair, for example with `npx web-push generate-vapid-keys`. Supply it securely. Changing the pair requires re-enrollment if the browser retains a subscription from the old key. Chromium/Firefox need a supported secure origin. iOS Web Push requires the home-screen web app and OS support. The notice worker handles push and tap events and leaves application requests on the network.
3. Android uses Firebase HTTP v1 with `DEVICE_PUSH_FCM_SERVICE_ACCOUNT_JSON`. Associate Firebase with the existing `com.voxelveda.app` application and configure the signed bundle workflow's `ANDROID_GOOGLE_SERVICES_JSON` secret with the matching Firebase client configuration. Retain the existing Play signing identity. Android notification permission is required where applicable.
4. iOS uses token-based APNs with `DEVICE_PUSH_APNS_KEY_ID`, `DEVICE_PUSH_APNS_TEAM_ID`, and `DEVICE_PUSH_APNS_PRIVATE_KEY`. Provision the existing bundle with Push Notifications and its matching signing profile. Use `DEVICE_PUSH_APNS_SANDBOX=true` only for an isolated development deployment targeting sandbox tokens. Store builds use production APNs. For both platforms the first push-capable upgrade requires a rebuilt, signed native binary on each test device.

## Verified release and activity sources

- Set matching `DEVICE_RELEASE_WEBHOOK_SECRET` in the server and GitHub Actions. The existing production marker verification workflow registers the web release only after the deployed app serves the expected revision and the production verification passes. The server also checks live readiness against the submitted SHA. The public action opens the update page and then the current web app. Applying it requires an affirmative navigation action and allows the user to save open work first.
- The `Verify store availability and record update notice` workflow checks current store availability every four hours on `main`. It also accepts explicit platform and version for an authorised check. Android uses `DEVICE_RELEASE_PLAY_READER_JSON`, a dedicated Play API account for the existing listing, separate from publishing credentials. It reads the highest completed production version code in an isolated Play edit snapshot and discards the uncommitted edit. Drafts, test tracks and staged rollouts are excluded. iOS checks `DEVICE_PUSH_APPLE_STORE_ID` (server and GitHub repository variable) against the Australian App Store storefront and the existing bundle ID. Native release actions open the corresponding store listing.
- Set `AI_TEAM_RECIPIENT_USER_IDS` to an explicit admin/super-admin user ID allowlist. Install a GitHub repository webhook for Workflow runs, Pull requests, Pull request reviews and Releases at `/api/ai-team/github`. Set `AI_TEAM_GITHUB_WEBHOOK_SECRET`, `AI_TEAM_GITHUB_REPOSITORY_ID` and optionally `AI_TEAM_GITHUB_REPOSITORY`. Events carry their real GitHub source and produce an internal card. A GitHub published release event in the private feed does not drive public update notices.
- For Codex activity, configure the same distinct `AI_TEAM_RUNNER_SECRET` on the application and a trusted, signed-in Codex CLI runner. Invoke a run through `node scripts/run-ai-team-notice.js <codex exec arguments>`. Set `AI_TEAM_RUNNER_ORIGIN` to the isolated test origin during verification. The wrapper reads actual Codex JSON lifecycle events, then sends the run identifier and outcome with a timestamped signature to `/api/ai-team/runner`. The child process does not receive the signing secret. Prompts, model output and private thread IDs stay local. Ordinary Codex sessions outside this wrapper do not produce events.
- Delivery and in-app preferences are independent. A never-linked installation is eligible only for published release notices. The notification body and tap payload omit team titles, names, task details and private links. The authenticated card contains the event summary and a local detail view.

## Test before activation

Use a disposable database and test provider project or isolated deployment. Verify an eligible owner/admin, an ordinary account and an installation that has never signed in. Check public-only opt-in, signed-out opt-in, permission denied, rotation, opt-out, account switch and private session revocation. Send one real test event from the signed producer, and prove an opted-in physical device displays and opens it after sign-in. Repeat the event and confirm the same installation does not receive a second notice. On the test rollout prove that the expected revision is publicly serving before recording a release. Check the right notification action with both warm and terminated app states, and record OS/build, provider acceptance and actual receipt separately. Keep test secrets and device tokens outside the PR.
