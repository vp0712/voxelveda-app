Profile photos now use one shared authenticated component across the profile page, admin header, staff header/sidebar/home and authorised staff directory. The previous dashboard adapter was absent from the page script loaders; its direct `img.src` request also could not carry the Bearer header used by retained sessions. The repaired loader includes `profile-avatar.js` before its dashboard adapter. The adapter fetches `/api/profile` and private image bytes with cookie credentials and the current Bearer header, then displays a shared in-memory Blob URL. Tokens, object-storage locations and signed public image URLs are never embedded in image URLs.

The component exposes `VoxelAvatar.mount`, `mountAll`, `refreshSelf`, `updateSelf`, `retrySelf` and `clear`. Self targets use `data-avatar-self`; directory targets use `data-avatar-user-id` and `data-avatar-name`. Revision changes refresh all mounted copies, while account switches, failed authentication and page exit revoke cached Blob URLs and clear displayed identity. Late responses from the previous account cannot create or display a cached image. Cross-tab updates carry only the user ID and revision. Initials represent missing or failed photos; loading has an explicit pending state, and the profile page offers a controlled retry. Profile preview uses the same authenticated Blob rather than another raw image URL. Profile fields clear on account change, and photo updates in another tab update the profile photo controls without overwriting unsaved text edits.

Original self endpoints remain `GET /api/profile`, `GET/POST/DELETE /api/profile/photo`. `GET /api/profile/staff/:id/photo` adds private directory retrieval. The backend allows self access, existing `MANAGE_USERS` or `VIEW_STAFF_HR` authority within a saved department boundary, or `VIEW_TEAM_TIMESHEET` access to direct managed staff. Customer/client/viewer/supplier/visitor contexts cannot gain cross-user photo access through a broad grant; unrelated managers and ordinary staff cannot retrieve another user's photo. Every image response is private/no-store, varies by Cookie and Authorization, declares its real image MIME type, and sets nosniff.

Photo upload accepts actual JPG, PNG and WebP bytes up to 5 MB. The profile UI prepares larger supported phone photographs before upload and offers an adjustable square crop with position and zoom controls. Server validation reads dimensions before decoding, caps source dimensions at 12,000 pixels and 24 megapixels, rejects animation and mismatched signatures, parses genuine image bytes, applies EXIF orientation once, strips source metadata through fresh encoding, and stores a 512×512 JPEG. Only two normalisation/legacy-decode operations can run concurrently; rendering uses a small destination canvas and does not allocate an intermediate canvas at full camera resolution. Existing configured scanner policy applies; required or failed closed scanning blocks replacement and preserves the current photo.

`profilePhotoService.ensureProfilePhotoSchema` adds four nullable columns to the existing `user_profiles` table: private object key, SHA-256, width and height. It does not rewrite historical users or photos. When the existing private object store is configured, new bytes are stored there and the database retains the reference; otherwise durable database BLOB storage remains supported. An explicitly configured but unavailable provider fails rather than silently changing storage. Legacy database photos remain readable and receive signature/dimension/decode checks. New object/DB references and actor audit commit atomically; duplicate photo content is a safe no-op. A failed registration cleans only its fresh unreferenced object, while an uncertain commit cannot delete referenced bytes. Replaced/removed private objects remain available to authorised audit/recovery operations; removal revokes the active profile reference.

`scripts/profile-avatar-test.js` uses genuine native-canvas JPG/PNG/WebP images and an injected EXIF-6 phone JPEG. It checks expected coloured pixels after rotation and square crop, alternate crop positions, invalid signature/dimension/zoom rejection, required scanning, bounded processing, database/object retrieval, duplicate save, audit rollback, lost-commit object preservation, own/team/department/customer permissions, response headers and historical-byte preservation on removal. `scripts/profile-avatar-component-test.js` executes the shared browser component in an isolated DOM fixture and verifies one authenticated photo fetch for multiple displays, immediate revision changes, stale-response isolation across accounts, explicit retry, staff endpoint use, external-URL rejection and complete Blob revocation. The existing timesheet-preference and file/API hardening checks remain applicable. Real database persistence and responsive browser evidence are recorded by the release verification workflow; fixture checks alone do not prove production access or phone-camera behavior on every device.
