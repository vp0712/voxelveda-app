## Proven causes and limits

The historical `markInvoicePaid` implementation at commit `5a1b5750` only ran `UPDATE invoices SET status='paid' WHERE id=?` and appended the literal activity **“Invoice marked as paid”**. It did not save an amount, payment date, method, source receipt or payment row. Later code independently summed non-void `invoice_payments` and coalesced an absent register to zero. The old view combined the saved status and this default, producing paid / paid 0 / outstanding full total. The supplied history matches that historical code path. This establishes a defect in the application's historical/manual settlement handling, without establishing whether the private invoice was actually paid or whether its payment rows are missing.

The fixture reproduces AUD 2,710.10 from stored net line amounts AUD 2,463.73 plus explicit stored 10% GST AUD 246.37. These are **fixture amounts**, not an assertion about the real invoice's lines or tax. No private production access/test account was supplied, so the exact payment and tax evidence for INV-823166 remains a blocker to record-level reconciliation. No production invoice has been modified and no historical payment has been manufactured.

The shared Admin/staff dialog supplied Cancel unconditionally while read-only callers supplied another Close callback. They performed the same dismissal. Legacy dialog scrolling rules made footers compete with content. The separate security verification layer was below the phone dialog's 40,000 layer, lacked a viewport height limit, and was covered by a loading overlay waiting for verification itself. A successful HTTP status containing HTML could also be treated as a successful mutation by legacy handlers. These paths were reproduced and repaired in the shared components.

## Implemented behavior

- A shared invoice domain calculates payment state and currency amounts with integer cents from valid, non-void original payment rows. Saved document status stays separate. A historical paid claim unsupported by complete payments, invalid/overpaid register or unavailable total yields **Payment details require review**, with paid/outstanding unknown rather than zero or a guessed value. Lists, details, customer statements, dashboard totals, reports and PDFs use the same projection/summary. Aggregate amounts containing unknown values remain unknown; full filtered totals are distinguished from page counts.
- Subtotal, GST and saved total are explicit. Original exclusive-tax records retain their treatment. Inclusive calculation is supported only for explicit stored inclusive metadata; missing tax is not assumed zero. An inconsistent tax/line snapshot is identified for review, and PDF generation refuses to fabricate agreement. Invoice creation now rounds and sums using the same currency-safe helpers.
- Read-only invoice view presents configured company details, saved customer details, recorded issue/due dates (missing dates labelled), labelled creation date when needed, structured quantities/unit prices/GST/amounts, totals, stored notes/terms, separate payments and activity. Activity shows known actor/action/local date without exposing raw internal JSON. Phone items become compact labelled cards; desktop remains an aligned table. View PDF and Download PDF are distinct. Edit, send, approval, payment, related RFQ, archive/restore and review remain scoped by the original permissions/statuses in More controls.
- PDF requests from that view include a hash of the same authoritative snapshot. A changed snapshot returns 409 and requires refresh. Parser-valid PDF bytes, application/pdf, safe filenames and retained immutable email documents remain enforced. Merely opening/closing a view does not save it.
- An explicit payment-review correction requires both original payment posting and void/correction permissions, server MFA verification, a version, stable request identity, evidence reference, reason and completeness acknowledgement. The transaction locks the invoice, rejects stale/changed evidence and records before/after/source/request data in the existing append-only invoice activity. Confirming a complete register creates no receipt. Recording a receipt requires an explicit evidenced amount/date/method/reference. The existing approved/sent lifecycle is restored only when supported by its history; otherwise the confirmed correction leaves Draft for authorised review. Duplicate/concurrent requests return the original result. Voids preserve the original payment row and audited reason. No new banking ledger, table, role or automatic bulk reconciliation was introduced.
- The shared dialog renders one Close for read-only views; specific action plus Cancel for forms/confirmations. Changed fields require discard confirmation, and busy writes cannot be casually dismissed. A scrollable body and compact fixed footer account for safe areas/visual viewport, Escape, Tab focus and return focus. The original field snapshot is captured before interaction, including edits before the first animation frame followed by blur. Repeated opens replace handlers and prevent stale invoice responses from reopening a closed view. Overlay replacements honour discard decisions. Staff shift information uses the same read-only component.
- Business Close RFQ is preserved as a separate authority-controlled, reasoned record action. Procurement Cancel requisition and Cancel purchase order use explicit labels and retain existing reason/permission/audit contracts. The generic dismiss button does not perform these actions.
- Shared write response handling rejects HTML/malformed success as an uncertain result and preserves the open form instead of announcing success. MFA still requires actual assurance level 3. Its own focus/viewport handling is repaired; the blocking brand loader is suspended only while the security dialog needs input, then resumes tracking the outstanding request.
